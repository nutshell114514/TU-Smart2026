# 全流程状态机流程优化建议

> 分析对象：当前工作区的 `base.py`、`task_leader.py`、`task_follow.py`、`config.py`。
>
> 本文只讨论“减少无效流程、让可以并行的事情并行、避免重复走路和重复定位”，不修改任何源码，也不重复《全流程状态机提速参数建议.md》里的单纯速度调参。

## 1. 先说结论

当前流程已经不是“每个状态都在白等”的结构。APPROACH 内部很多旧的停车保持已经取消，SEARCH 的每次 sweep 握手也已经取消。因此下一阶段最有效的优化，不是再随意删除安全门，而是下面五件事：

1. **让找目标与车辆移动并行**：主车在去搜索线、RECOVER 等从车的静止阶段也观察下一个目标，发现后直接进入 APPROACH。
2. **减少 ROUTE 后的重复接近**：绕障横移结束后，不要无条件后退 6 cm 再完整绕行、贴靠；满足几何条件时走快速恢复路径。
3. **让最终归位更早并行**：从车不必一直等到主车进入 DONE 才开始自己的最终重定位；主车路径已经安全分离后即可放行从车。
4. **删除结束阶段的非任务动作**：如果主车最终自转一圈不是比赛要求，直接取消，可固定节约约 1 秒。
5. **降低每循环的系统开销**：当前每个主循环都执行 `gc.collect()`，LCD 也每循环刷新。这会降低控制、视觉和通信的有效刷新率，先优化它们通常比继续提高电机速度更稳。

我建议优先做低风险的“观察前移”和“纯空耗删除”，再做 ROUTE 快速恢复，最后才做 RECOVER/RELOCALIZE 的并行化。

---

## 2. 当前流程基线

当前主流程可以概括为：

```text
BOOT_SYNC
    ↓
SEARCH
    ↓ 找到目标
APPROACH
    ↓ 两车完成槽位接近
WAIT_READY
    ↓ 目标、队友和走廊条件满足
PUSH_SYNC
    ↓ 正常出黄线
RECOVER
    ↓
SEARCH（仍有目标）
    或
RELOCALIZE → DONE（全部完成）
```

当前已经完成、后续应继续保留的优化：

- SEARCH 的第一次和后续 sweep 前都不再等待从车握手。
- 从 RECOVER 带入 SEARCH 的侧阵型会持续保持，不再在第二次 sweep 恢复成一前一后。
- 普通网球 PUSH 一旦开始，就不会因为网球丢失而退出 PUSH；仍然正常计数并运行到出黄线。
- 普通网球的斜避障方向由预避障结果锁定，推送中不会因为后续观测突然反向。
- 上述“普通 PUSH”规则不扩展到单独的 ROUTE 流程。

这些规则已经直接减少了编队等待和网球掉落风险，本文不建议撤销。

## 3. 优先级总表

| 优先级 | 优化项 | 主要节约 | 预计收益 | 风险 |
|---|---|---:|---:|---:|
| P0 | SEARCH 去搜索线途中也允许锁定目标 | 省掉剩余到线和后续 sweep | 单次约 0.2 秒到数秒 | 低—中 |
| P0 | RECOVER 静止等从车时预选下一个目标 | 把等待时间变成识别时间 | 单次约 0.2 秒到数秒 | 中 |
| P0 | 限频 LCD、条件式 GC | 减少每循环阻塞和视觉/通信滞后 | 全程持续收益 | 中 |
| P0 | 若非比赛要求，取消主车 DONE 自转 | 删除 300 ms 停稳和 360°自转 | 约 0.97 秒 | 低 |
| P1 | VDOCK 无球时分情况缩短 1000 ms 等待 | 避免明知无球仍等满 | 每次最多约 0.65–0.75 秒 | 中 |
| P1 | APPROACH 后半段提前观测 ROUTE 走廊 | 缩短 WAIT_READY 决策时间 | 每次约 10–数百 ms | 低—中 |
| P1 | ROUTE 横移结束后条件式快速恢复 | 少走 6 cm 后退和部分重复接近 | 每次约 0.3–1.5 秒以上 | 中 |
| P1 | ROUTE 的 250 ms 固定稳定改成提前完成 | 稳定即走，不强制等满 | 每次 0–0.2 秒 | 中 |
| P1 | 斜推固定 100 ms 延时改成确认帧 | 少等固定时间，且同步更可靠 | 每次斜推事件约 0.06–0.16 秒 | 中 |
| P2 | 提前下发从车的临时 APPROACH 规划 | 减少从车在 ORBIT 起点硬等 | 一个或多个无线周期 | 中 |
| P2 | 保存搜索覆盖进度 | 避免每个目标后重复扫已覆盖区域 | 与目标分布有关，可能数秒 | 中—高 |
| P2 | 按完整任务代价选目标 | 少走总路程、少触发 ROUTE | 与场景有关 | 高 |
| P2 | 主车重定位中途提前放行从车 | 最终两车归位更充分并行 | 约 0.5 秒到数秒 | 高 |
| P3 | RECOVER 后主车边去搜索线、从车边完成侧阵型 | 减少主车静止等编队 | 与从车恢复耗时有关 | 高 |

说明：上表是依据状态机结构给出的量级，不是实测承诺。真正收益应以状态进入/退出时间戳统计为准。

## 4. BOOT_SYNC：只清理一周期交接，不删启动安全门

### 4.1 当前情况

主从车都存在一个“收到/发出启动命令后，下一任务循环再开始横移”的 WAIT_FRAME 子阶段。它主要用于把通信边沿和运动边沿分开，实际只多一个控制周期。

摄像头就绪和无线对车就绪则是真正的启动条件；蜂鸣间隔主要是提示，不是正常运动的主要瓶颈。

### 4.2 可优化项

如果实测启动同步非常稳定，可以把 WAIT_FRAME 改成同周期完成状态设置、立即发送一次无线帧，然后直接发出首个运动请求。

### 4.3 评价

- 预计只省一个循环，通常是几毫秒到几十毫秒。
- 收益很小，不值得为了它削弱摄像头/无线 ready 门。
- 建议放在所有主要优化之后。

### 4.4 不建议删除

- 摄像头有效帧门。
- 对车通信新鲜度门。
- 启动失败时的超时保护。

## 5. SEARCH：最值得优化的是“边走边找”和“不要重复扫”

### 5.1 去搜索线途中也允许锁定目标

当前目标确认只在以下搜索子状态运行：

- `_SEARCH_FIRST_DIAG`
- `_SEARCH_SWEEP`
- `_SEARCH_STEP_FORWARD`

而 `_SEARCH_MOVE_TO_POINT` 没有进入 `target_state`。这意味着 RECOVER 后主车向下一条搜索线移动时，即使画面已经看到可用目标，也要先走到搜索线，再开始 sweep 后才会锁定。

建议：

- 将 `_SEARCH_MOVE_TO_POINT` 纳入目标观察和稳定确认。
- 一旦目标满足原有连续帧确认，立即停止当前去线动作，转入 APPROACH。
- 保留“目标必须是剩余对象、ID 有效、连续帧稳定、不是刚推出对象残影”等现有约束。
- `_SEARCH_TURN_YAW` 可先只观察、不锁定；车辆转动时物体世界坐标误差更大，等航向稳定再确认。

收益：省掉“走完剩余搜索线距离 + 开始 sweep 后再次看到目标”的时间，是 SEARCH 内低改动、高收益的一项。

### 5.2 RECOVER 等从车时预选下一个目标

主车完成 BACK、黄线坐标修正和 YAW_FIX 后，会进入 `_SUB_WAIT_FOLLOWER_FOLLOW`，此时主车静止，只等从车完成视觉跟随/侧阵型。

当前 RECOVER 模式下：

- 黄线识别开启。
- 普通目标模型没有开启。
- 主车静止等待期间没有为下一次 SEARCH 做目标确认。

建议的安全做法：

1. VIS_FIX 和 YAW_FIX 阶段仍以黄线为唯一高优先级，不抢占视觉。
2. 只在 `_SUB_WAIT_FOLLOWER_FOLLOW` 静止阶段关闭不再需要的黄线通道，打开目标模型。
3. 只做“候选目标预锁定”，不立刻让主车开走。
4. 从车 ready 后，如果候选仍新鲜且连续确认有效，直接进入 APPROACH；否则照常进入 SEARCH。

这样没有取消 RECOVER 的编队安全门，只是把原本纯等待的时间用于识别。

### 5.3 一次黄线修正用完后关闭 SEARCH 线识别

`_search_line_fix_used` 已确保每轮 SEARCH 最多触发一次黄线补坐标，但 `_OPENART_LINE_ENABLE` 仍然在整个 SEARCH 模式保持开启。

如果 OpenART 的线识别和物体模型会争用处理时间，建议在 `_search_line_fix_used=True` 后关闭线通道，直到离开 SEARCH。这样后续帧只服务目标识别。

注意：先确认 OpenART 固件是串行/分时推理。若两个开关只是消息过滤、不会影响推理帧率，则这项只有代码清理价值，没有时间收益。

### 5.4 删除非 RECOVER 入口的 120 ms 到点保持

首次 SEARCH 或异常回退走到预设点后，会进入 `_SEARCH_HOLD_POINT` 并固定保持 `_SEARCH_POINT_HOLD_MS=120`，然后才开始 sweep。

现在 sweep 前的从车握手已经取消，这 120 ms 不应再承担“等从车”的职责。建议改为条件式：

- 位置进入阈值；
- 航向进入阈值；
- 估计平移速度低于阈值；
- 满足后立即开始 sweep；
- 120 ms 仅保留为最大稳定等待，而不是固定下限。

正常 RECOVER 入口目前已经能直接衔接 sweep，不受这项影响。

### 5.5 保存搜索覆盖进度

每完成一个目标后重新 SEARCH，当前规划更依赖固定搜索线和当前推出边。它能工作，但可能重新覆盖刚扫过的区域。

建议增加轻量搜索记忆：

- 记录本轮已覆盖的横扫带编号。
- 记录每条带的最后 sweep 方向。
- PUSH/RECOVER 后，从离当前位置最近的未覆盖带继续。
- 对长时间未更新的覆盖标记设置失效时间，避免动态目标移动后永远不复查。

这项对目标稀疏、每个目标间隔远的场景收益很大；对目标集中场景收益较小。

### 5.6 用“总任务代价”代替只看最近目标

长期可把选目标代价写成：

```text
总代价 = 车到目标距离
       + 目标到对应黄线距离
       + 预计 RECOVER 后到未搜索区距离
       + 障碍/ROUTE 惩罚
       + 两车形成推送槽位的代价
```

这样有时会选择稍远一点、但更容易推出且推出后更接近未搜索区域的目标，总流程反而更短。

这是调度层改造，必须用多局日志验证，不建议作为第一批修改。

## 6. APPROACH：把等待变成提前计算和提前观测

### 6.1 提前下发从车临时规划

侧向入场的部分分支会将 `_approach_follower_dir_pending` 置位。此时从车可以完成 FACE 和半径调整，但到达 AP_ORBIT 起点后必须停车，等主车收到其实时姿态，再由 `_finalize_pending_follower_plan()` 计算最终环绕方向。

这个设计很安全，但可能产生一个或多个无线周期的硬等待。

建议：

- SEARCH → APPROACH 时，先用主车已有的从车世界坐标、航向和目标坐标计算一个临时方向并立即下发。
- 从车先按临时方向进入低速 PRE_ORBIT，不立即高速绕行。
- 主车拿到更新后的从车姿态后，仅在方向冲突或路径交叉时修订。
- 若修订会造成反向，必须先停稳再改，不能运动中突然反转。

这项收益不是固定秒级，但可以让 APPROACH 的主从动作更重叠。

### 6.2 在 CLOSE/VDOCK 后半段提前观测 ROUTE 走廊

目前 ROUTE 走廊观测主要在 WAIT_READY 中执行。车辆进入 WAIT_READY 后才开始积累障碍信息，会让 WAIT_READY 承担额外决策延迟。

建议：

- 在目标姿态已稳定的 CLOSE 后半段和 VDOCK 阶段，提前调用“只观测、不生成动作”的走廊识别。
- 进入 WAIT_READY 后再结合两车观测正式决定直推还是 ROUTE。
- 提前观测不得在 APPROACH 中直接发起横移，避免槽位尚未完成时改变流程。

这相当于把感知流水线前移，不删除任何推送安全条件。

### 6.3 VDOCK 的 1000 ms 无球等待分情况处理

从车 VDOCK 有 `_VDOCK_BALL_WAIT_MS=1000`。某些目标在球信息不可用时，会等满 1 秒才让物体几何完全接管。

建议区分两种情况：

- **刚才看见球、随后短暂丢失**：继续保留 1000 ms，给视觉遮挡恢复机会。
- **本次 VDOCK 从未获得有效球信息，或该类目标本来就不依赖球**：物体位置连续稳定后约 250–350 ms 即可降级，不必等满 1000 ms。

`_VDOCK_HOLD_MS=150` 建议保留，它承担最终贴靠稳定确认；可以考虑让这 150 ms 同时积累 WAIT_READY 所需证据，而不是两个状态各自重新计时。

## 7. WAIT_READY：不能删，但可以让它只做最终裁决

WAIT_READY 同时确认：

- 本车目标仍在合适位置；
- 对车模式、ready 和无线帧新鲜；
- ROUTE 走廊是否安全；
- 两车是否能同步进入 PUSH。

因此不建议取消整个 WAIT_READY。更合理的目标是：让 APPROACH 已经提前完成大部分观测，WAIT_READY 只做最后一帧裁决。

### 7.1 可做的小优化

- 同一循环内缓存一次 `target_still_ok()` 结果，不重复计算和读取变化中的视觉数据。
- 同一循环内缓存一次 `peer_ready`，统一复用模式、ready 和时间戳判断。
- APPROACH → WAIT_READY 状态边沿立即发送无线帧，不额外等普通 10 ms 周期。
- ROUTE 候选由 APPROACH 预观测，WAIT_READY 只确认候选仍新鲜。

这些主要降低抖动和一两个通信周期，不会带来大幅固定节约。

### 7.2 不应当成正常耗时删除的参数

`_READY_CLOSE_BAD_MS=2000` 是目标姿态持续恶化后的异常恢复门，不是正常路径固定等待。把它调得很短，容易因一两帧抖动重复回 APPROACH，反而更慢。

## 8. PUSH_SYNC：重点优化 ROUTE 恢复，不动网球承诺

### 8.1 ROUTE 后不再无条件后退 6 cm

ROUTE 横移完成后，主从车都会设置强制推送角接近请求：

- `_approach_req = _APPROACH_REQ_FORCED_PUSH_YAW`
- `_approach_do_back = 1 if True else 0`

其中 `1 if True else 0` 实际就是无条件后退。随后两车执行约 6 cm BACK，再重新 ORBIT/CLOSE/VDOCK，最后才回普通 PUSH。

这条路径很稳，但重复动作最多，是 ROUTE 中最值得优化的位置。

建议增加两个恢复分支：

```text
ROUTE 横移完成
    ├─ 几何仍好 → FAST_RESTORE：跳过 BACK，直接 PRE_ORBIT/ORBIT 或短 CLOSE
    └─ 几何变差 → SAFE_RESTORE：保留原 6 cm BACK + 完整重接近
```

FAST_RESTORE 至少应同时满足：

- 两车仍识别到同一目标，目标 ID 没变。
- 目标前向距离、横向误差处于比最终贴靠略宽的安全带内。
- 两车航向间隔和车间距安全。
- ROUTE 横移过程中没有明显目标滚动或大位移。
- 对车数据新鲜。

若任一条件不满足，仍走当前完整恢复路径。不要直接全局删除 6 cm BACK。

### 8.2 `_PUSH_ROUTE_SETTLE_MS=250` 改成条件式提前结束

当前 ROUTE 收尾固定稳定 250 ms。建议改为：

- 两车目标误差连续若干帧进入稳定带后立即结束 settle。
- 250 ms 作为最大等待或低速不稳定时的兜底。
- 不能只用单帧位置满足，至少要求连续帧或速度低于阈值。

正常情况下可节约 0–200 ms；目标仍在滚动时不会提前。

### 8.3 固定 100 ms 推送时序改成显式确认

普通 PUSH 起步和斜推切换存在若干 100 ms 固定错峰：

- `_PUSH_START_LEADER_ORANGE_LEAD_MS=100`
- `_PUSH_START_DELAY_LEADER_PURPLE_MS=100`
- `_PUSH_GO_ADVANCE_MS=100`
- `_PUSH_DIAG_LEADER_DELAY_MS=_PUSH_GO_ADVANCE_MS`

这些延时用于避免两车接触时序不一致，不能直接改成 0。更好的做法是：

1. 主车发送带序号的阶段命令。
2. 从车回报已收到并已进入对应硬保持/斜推状态。
3. 主车收到匹配序号后立即进入下一阶段。
4. 100 ms 保留为未收到确认时的最大兜底。

这样正常无线链路下可能 20–40 ms 就能完成同步，丢帧时仍有原安全上限。

### 8.4 非网球目标丢失时融合两车视觉

普通非网球 PUSH 的目标丢失主要由主车自身视觉确认。若主车被遮挡、从车仍能看见目标，主车可能误进入丢失恢复。

可在无线帧中增加“当前目标仍可见 + 新鲜度”信息：只要任一车仍可靠看见同一目标，就不因单车遮挡立即进入旋转找回。

这是异常路径优化，正常比赛没有丢失时不节约固定时间，但能避免一次代价很高的误恢复。

### 8.5 网球规则保持不变

以下行为是当前任务约束，不作为提速项修改：

- 普通网球 PUSH 开始后，即使视觉丢失也不退出。
- 一直运行到正常离开黄线，并正常将网球数量减一。
- 斜避障方向必须与预避障一致，推送中不得反向。
- ROUTE 不套用“不允许退出普通 PUSH”的规则。

## 9. RECOVER：先利用等待，再考虑减少等待

### 9.1 第一阶段只做“等待期间识别”

最稳的优化就是第 5.2 节：主车在 `_SUB_WAIT_FOLLOWER_FOLLOW` 保持不动，但提前观察下一个目标。它不会改变从车恢复轨迹，也不会让主车提前离开。

### 9.2 第二阶段再考虑主车提前去搜索线

当前主车会等从车完整达到视觉跟随/侧阵型条件，然后才离开 RECOVER。更激进的方案是：

- 从车已重新看见主车；
- 无线数据新鲜；
- 车距处于安全范围；
- 下一搜索线距离足够长；

满足后主车以较低速度先去搜索线，从车在移动环境中完成剩余侧阵型收敛。

这符合此前“从车动态修正”的方向，但风险明显高于取消 sweep 握手，因为此时从车可能刚从边界退出，姿态和距离误差更大。

推荐只在以下条件同时满足时启用：

- 从车视觉已经稳定看到主车若干帧，而不只是单帧看到。
- 主车前进方向不会把从车再次逼向刚推出的黄线。
- 去搜索线至少还有一段足够长的直线，能让从车收敛。
- 设车距过近、视觉再次丢失时主车减速，而不是继续全速拉开。

这项属于第三阶段优化，不建议第一批修改。

### 9.3 不建议删除的 RECOVER 动作

- 推出后约 8 cm BACK：用于脱离物体和边线。
- 黄线坐标修正：用于抑制多次推送后的里程计漂移。
- YAW_FIX：用于保证下一轮世界坐标和侧阵型方向正确。
- 子状态交界处的 hard hold：用于清掉上一段速度和积分残留。

这些动作看起来占时，但删除后会把误差传到下一轮 SEARCH/APPROACH，常常得不偿失。

---

## 10. RELOCALIZE：让最终归位更早并行

### 10.1 缩短 RECOVER → RELOCALIZE 的模式交接，但保留确认

全部目标完成时，主车在 RECOVER 接受的是“从车仍处于 RECOVER 且 ready=2”；主车切到 RELOCALIZE 后，`_RELOC_FORMATION_WAIT` 等待的是“从车已经切到 RELOCALIZE 且重新发布 ready=2”。两者看起来相似，但后者也承担了确认从车已经收到新模式的作用，不能当成完全重复而直接删除。

可做的小优化是：

- 主车进入 RELOCALIZE 时立即发送状态边沿。
- 从车若刚才已有新鲜的视觉跟随稳定证据，可把该证据带入 RELOCALIZE，减少重新累计时间。
- 主车仍必须至少收到一帧“从车模式已经是 RELOCALIZE、ready=2”的确认，才能进入 `_RELOC_X_TURN`。

这通常只节约一个或少量无线周期，优先级不高，但不会破坏模式交接安全性。

### 10.2 主车路径安全后提前放行从车

当前从车在 `_RELOC_FOLLOW_LEADER` 中持续跟随，只有看到主车进入 DONE 后，才开始自己的脱离、PREMOVE、X/Y 修正。主车进入 DONE 后，两车的 DONE 移动会有一定并行，但从车自己的重定位启动得仍然偏晚。

建议主车增加“允许从车自归位”的明确阶段信号，例如：

- 保守方案：主车完成 X 修正、进入 Y 方向修正后放行从车。
- 激进方案：主车到达 PREMOVE 目标并进入 X_DRIVE 后放行。

从车收到信号后不再视觉跟随主车，提前开始自身的安全脱离和重定位。必须先验证两条轨迹不会交叉。

### 10.3 主从 DONE 目标必须分开

`config.py` 当前配置为：

```python
_DONE_TARGET_POS = (
    (25.0, -50.0),  # 主车
    (25.0, -50.0),  # 从车
)
```

两车最终目标完全相同。即使现有时序可能避免同时到点，这仍会让最终停车互相阻挡；如果要加强重定位并行，这个问题必须先解决。

推荐将目标按左右分开，例如先试验接近各自初始 X 的位置：

```text
主车：(40, -50) 附近
从车：(10, -50) 附近
```

具体值要结合场地黄线、车宽和最终朝向实测，不能只按示例直接写死。

### 10.4 不建议完全取消最终重定位

最后一次 RECOVER 通常只针对刚推出的那一条边修正一个轴和航向；最终回场需要两个轴都可信。因此在没有更可靠外部定位替代前，不建议直接跳过 RELOCALIZE。

## 11. DONE：存在最明确的纯空耗

### 11.1 主车 360°自转

主车到达 DONE 目标后：

1. 固定保持 300 ms。
2. 进入 `_DONE_SPIN`。
3. 以 `_DONE_SPIN_RATE_DPS=540` 累计旋转 `_DONE_SPIN_TOTAL_DEG=360`。

理论自转时间约为：

```text
360 / 540 = 0.667 秒
```

加上 300 ms 保持，总计约 0.97 秒。

如果自转只是结束展示，不是比赛判定要求，建议整个删除。它是全流程中最明确、最稳定、风险最低的固定节约项。

如果自转必须保留，300 ms 固定保持可以改为：最低 50 ms，并在编码器估计速度已经接近 0 时提前开始；300 ms 作为最大等待。

### 11.2 从车 DONE 的 300 ms 分支是无动作变化

从车到达 DONE 点后先 `request_hold()`，计时 300 ms 后仍然调用相同的 `request_hold()`，没有进入新的子状态，也没有产生新动作。

这个计时分支可以直接清理。它未必改变比赛结束时间，但能减少无效状态逻辑，让 DONE 行为更明确。

## 12. 系统层：每循环 GC 和 LCD 可能是隐藏的大头

### 12.1 当前行为

`base._loop_step()` 每一循环依次执行：

```text
通信更新 → task.update() → LCD/debug_view_update() → gc.collect()
```

源码注释已经指出，`task.update() + LCD + gc.collect()` 可能把循环拉长到 15–40 ms，使 OpenART 位姿旧一拍。

另外，主从车每次 `enter_mode()` 还会执行一次 `gc.collect()`；初始化阶段也有多次连续收集。

### 12.2 推荐改法

不要直接彻底取消 GC，而应改为条件式：

- 每次状态切换保留一次 GC。
- 正常循环仅在 `gc.mem_free()` 低于实测安全阈值时收集。
- 或限制为每 100–200 ms 最多一次，优先放在 WAIT_READY、RECOVER 等保持阶段。
- 尽量预分配高频数组和帧缓冲，避免循环内创建临时对象。
- 记录单次 GC 耗时和最低空闲内存，验证不会发生内存不足。

### 12.3 LCD 限频

`_DEBUG_LCD=1` 且主循环中无条件调用 `debug_view_update()`。比赛运行时建议：

- LCD 只以 5–10 Hz 刷新，而不是每个控制周期刷新。
- 或提供 COMPETITION 开关，正式运行关闭 LCD，调试时开启。
- 错误页面和关键状态提示仍可立即刷新。

这两项未必直接减少某个状态的固定秒数，但会提高视觉、无线和控制状态机的实际刷新率，减少“参数加快后反而抖动”的问题。

## 13. 推荐的新流程

推荐最终演进为：

```text
BOOT_SYNC
    ↓ 保留相机/无线 ready
SEARCH
    ├─ sweep / forward 正常找目标
    └─ 去搜索线途中同样找目标
    ↓
APPROACH
    ├─ 两车并行靠位
    ├─ 临时规划先下发、必要时修订
    └─ 后半段提前观测推送走廊
    ↓
WAIT_READY
    └─ 只做目标、队友、走廊的最终确认
    ↓
PUSH_SYNC
    ├─ 普通直推/斜推
    ├─ 网球保持现有不退出和方向锁定规则
    └─ ROUTE 完成后：几何好走 FAST_RESTORE，否则完整恢复
    ↓
RECOVER
    ├─ 主车完成 BACK、黄线和航向修正
    ├─ 静止等从车时预选下一目标
    └─ 后期验证通过后，允许边去搜索线边收敛侧阵型
    ↓
    ├─ 有目标：候选有效则直接 APPROACH，否则 SEARCH
    └─ 全部完成：RELOCALIZE
                      ├─ 主车路径安全后提前放行从车
                      └─ 两车前往不同 DONE 目标
                              ↓
                             DONE
                              └─ 若无比赛要求，不自转
```

---

## 14. 推荐实施顺序

### 第 0 批：先加测量，不改决策

记录每次状态进入/退出时间，以及以下统计：

- 每个大状态耗时。
- SEARCH 各子状态耗时和发现目标时车辆所在子状态。
- WAIT_READY 等的是目标、对车，还是 ROUTE 观测。
- ROUTE 后 BACK、ORBIT、CLOSE、VDOCK 各自耗时。
- RECOVER 主车完成修正后等从车多久。
- 主循环平均/最大周期、LCD 耗时、GC 耗时和最低空闲内存。

没有这些数据，很容易优化一个实际只占 50 ms 的分支，却忽略每局重复数秒的等待。

### 第 1 批：低风险和明显空耗

1. SEARCH 的 `_SEARCH_MOVE_TO_POINT` 允许目标确认。
2. SEARCH 黄线修正用完后，验证并关闭不再需要的线识别。
3. 删除从车 DONE 的无动作 300 ms 分支。
4. 如果规则允许，删除主车 DONE 自转。
5. 限制 LCD 刷新频率。
6. 同循环缓存 WAIT_READY 的重复检查结果。
7. APPROACH/WAIT_READY 状态边沿立即发送无线状态帧。

### 第 2 批：感知流水线和条件式等待

1. RECOVER 静止等从车时预选目标。
2. APPROACH 后半段提前观测 ROUTE。
3. VDOCK 无球等待按“曾经看见/从未看见”分流。
4. `_SEARCH_POINT_HOLD_MS` 改成速度/姿态条件提前结束。
5. `_PUSH_ROUTE_SETTLE_MS` 改成连续稳定帧提前结束。
6. 每循环 GC 改成内存阈值或限频收集。

### 第 3 批：ROUTE 快速恢复

1. 增加 FAST_RESTORE 判定。
2. 保留原 6 cm BACK 作为 SAFE_RESTORE。
3. 先只对白盒测试中目标几乎不移动的 ROUTE 开启。
4. 统计快速恢复失败率、重新接近次数和推送掉物率，再逐步扩大条件。

### 第 4 批：全局并行和任务调度

1. 主车重定位中途提前放行从车。
2. 分开主从 DONE 目标并做轨迹冲突验证。
3. RECOVER 后允许主车提前去搜索线。
4. 保存搜索覆盖进度。
5. 使用完整任务代价选择目标。

这一批对总时间潜力最大，但会改变主从相互位置和全局路径，必须最后做。

## 15. 验收标准

每项优化不要只看“平均快了多少”，至少同时检查：

| 指标 | 目的 |
|---|---|
| 全流程中位数和最慢 10% 耗时 | 防止平均变快但偶发卡死 |
| 每个状态/子状态耗时分布 | 找出真正等待点 |
| 目标丢失和重新 SEARCH 次数 | 防止提前切换降低识别稳定性 |
| APPROACH 重启次数 | 检查快速规划和 VDOCK 降级是否过激 |
| ROUTE 后二次恢复率 | 检查 FAST_RESTORE 是否真的可靠 |
| 推送掉物率，尤其网球 | 速度收益不能以成功率换取 |
| 两车最小距离 | 验证并行化没有碰撞风险 |
| 无线帧最大间隔 | 检查 LCD/GC 和高速状态切换影响 |
| 主循环最大周期 | 验证系统层优化是否有效 |
| 最终停车距离 | 验证分开 DONE 目标和并行归位 |

建议每次只启用一类优化，至少比较“原版 / 新版”各 20 局。只有成功率不下降、最慢局不明显恶化，才继续下一批。

## 16. 明确不建议为了提速删除的逻辑

- BOOT 的相机和无线就绪检查。
- WAIT_READY 的目标有效、对车新鲜和走廊安全检查。
- PUSH 开始的主从同步本身；应以确认帧优化，不能直接取消。
- PUSH → RECOVER 和 RECOVER 子阶段边界的 hard hold。
- 推出后的 8 cm BACK。
- 黄线坐标修正和航向修正。
- 无线超时、视觉超时等异常兜底。
- 从车 SEARCH 接近场地边界时的提前停止保护。
- 最终双轴重定位，除非已有等价且更可靠的外部定位。
- 普通网球 PUSH 不退出、正常计数、避障方向锁定的现有规则。

## 17. 最推荐先做的五项

如果只选五项，我建议顺序如下：

1. **SEARCH 去搜索线途中识别并直接锁定目标。**
2. **RECOVER 静止等待从车时预选下一目标。**
3. **限制 LCD 刷新，并将每循环 GC 改为可测量的条件式收集。**
4. **ROUTE 后增加 FAST_RESTORE，保留现有完整恢复作为兜底。**
5. **若比赛不要求，删除主车 DONE 的 300 ms + 360°自转。**

这五项覆盖了“移动时找目标、等待时找目标、系统循环减负、减少重复路线、删除纯展示动作”，比把所有电机参数同时再提高一档更容易获得稳定的全流程收益。
